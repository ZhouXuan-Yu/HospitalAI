# 处方推荐前端后端接口对接文档

> 版本：v1.1
> 
> 适用页面：医生处方推荐工作台 `/doctor/workbench/{encounterId}`
> 
> 对接对象：HospitalAI Web 前端、Core API、规则服务、证据服务、HIS 草稿适配器
> 
> 医疗边界：本模块只生成推荐和处方草稿，不生成正式医嘱，不替代医生诊断和最终处方责任。

## 1. 对接目标

医生打开页面后，前端必须能够完成以下链路：

```text
科室患者列表
  -> 患者基本信息与当前就诊
  -> 确定性安全审查
  -> 首选处方方案
  -> 备用方案摘要
  -> 药品详情与证据按需展开
  -> 医生采纳、修改或驳回
  -> 处方草稿状态和审计结果
```

页面第一屏的业务优先级：

1. 当前患者是谁。
2. 患者有哪些不可用药风险或信息缺失。
3. 首选方案具体开哪些药、如何使用、为什么推荐。
4. 医生是否可以采纳，采纳后只生成什么状态。

不允许前端以 `DeepSeek`、模型名称、检索过程或长篇技术日志作为处方推荐主标题。

## 2. 公共接口约定

| 项目 | 约定 |
|---|---|
| Base URL | 同源 `/api`，医院部署由网关转发 |
| 编码 | `UTF-8` |
| 时间 | ISO-8601 UTC，例如 `2026-08-10T08:30:00Z` |
| Content-Type | `application/json` |
| 身份 | 生产使用 OIDC/医院 SSO；开发联调可使用 `X-HospitalAI-Role`，不得进入生产凭证 |
| 幂等 | 所有写接口必须携带 `Idempotency-Key` |
| 追踪 | 建议携带 `X-Request-Id`，响应返回 `traceId` |
| 版本并发 | 写入时校验 `recommendationVersion` 或 `dataVersion`，冲突返回 `409` |
| 数据来源 | 事实必须带来源、来源标识、采集时间、数据版本和缺失状态 |
| 医疗安全 | 阻断由 Core API/Java 确定性执行，前端不得自行放行 |

### 2.1 通用错误格式

```json
{
  "code": "RECOMMENDATION_BLOCKED",
  "message": "已确认药物过敏，不能采纳当前候选方案",
  "traceId": "trc-20260810-000001",
  "details": {
    "ruleIds": ["HR-ALG-001"],
    "candidateId": "C-AMOX",
    "fieldErrors": []
  }
}
```

| HTTP | 前端处理 |
|---|---|
| `400` | 请求格式错误，提示字段问题 |
| `401` | 跳转认证或显示身份过期 |
| `403` | 显示无科室/患者范围权限，不展示可编辑控件 |
| `404` | 患者、就诊或推荐不存在，返回列表重新选择 |
| `409` | 数据版本冲突，重新读取后要求医生确认，不静默覆盖 |
| `422` | 规则或字段校验失败，显示具体字段和规则 |
| `429` | 显示稍后重试，不重复提交 |
| `503/504` | 显示服务降级；患者事实和硬规则可继续展示，不能伪造推荐 |

## 3. 接口总览

| 页面动作 | 方法 | 路径 | 必要性 | 说明 |
|---|---|---|---|---|
| 加载科室患者列表 | `GET` | `/api/worklist` | 必须 | 左侧只展示摘要任务 |
| 打开处方推荐 | `GET` | `/api/workbench/{encounterId}` | 必须 | 返回患者、规则、候选和依据 |
| 延迟加载患者详情 | `GET` | `/api/patients/{patientId}/context` | 建议 | 左栏展开或详情抽屉使用 |
| 延迟加载药品详情 | `GET` | `/api/drugs/{drugCode}` | 建议 | 药品详情表格使用；也可由工作台响应内嵌 |
| 采纳/修改/驳回 | `POST` | `/api/recommendations/{recommendationId}/decision` | 必须 | 只能创建推荐决策和处方草稿 |
| 查询处方草稿状态 | `GET` | `/api/prescription-drafts/{draftId}` | 建议 | 采纳后查看草稿状态，不等同正式医嘱 |
| 查看受控证据原文 | `GET` | `/api/evidence/chunks/{evidenceId}` | 建议 | 右侧证据抽屉定位原文 |

## 4. 患者工作列表接口

### 4.1 请求

```http
GET /api/worklist?departmentId=RESPIRATORY&status=pending&page=1&pageSize=20&keyword=
Accept: application/json
Authorization: Bearer <access-token>
```

当前前端兼容直接返回数组；正式项目建议使用分页 envelope。

### 4.3 字段要求

| 字段 | 类型 | 必填 | 说明 |
|---|---|---:|---|
| `encounterId` | `string` | 是 | 当前就诊唯一标识 |
| `patientId` | `string` | 是 | 内部统一患者标识 |
| `displayName` | `string` | 是 | 生产环境按医院脱敏策略返回 |
| `sex` | `string` | 是 | `M/F/U` |
| `age` | `integer` | 是 | 当前就诊时年龄，不能为负数 |
| `department` | `string` | 是 | 当前负责科室 |
| `diagnosis` | `string` | 是 | 当前主要诊断摘要 |
| `dataVersion` | `integer` | 是 | 患者/就诊事实版本 |
| `admittedAt` | `date-time` | 是 | 入院或就诊开始时间 |
| `recommendationStatus` | `enum` | 建议 | `pending_review/blocked/decided/expired` |
| `recommendationSummary` | `string` | 建议 | 左侧快速查看的首选方案摘要，不放长理由 |
| `riskLevel` | `enum` | 建议 | `none/info/strong/block` |
| `pendingReason` | `string` | 建议 | 待处理原因 |

### 5.3 前端必须使用的响应字段

| 模块 | 必须字段 | 前端用途 |
|---|---|---|
| 患者身份 | `patient`、`encounter` | 首屏身份、科室、诊断、就诊号 |
| 原始事实 | `facts` | 左侧患者详情和来源追溯 |

| 状态 | `recommendationVersion`、`stages`、`aiStatus` | 版本控制和降级提示 |

### 5.4 结构化药品字段要求

前端不能从一段自然语言 `regimen` 中猜测剂量、频次或给药途径。后端应返回 `medications` 数组，并满足：

| 字段 | JSON 类型 | 说明 |
|---|---|---|
| `medicationId` | `string` | 当前候选中的药品条目唯一标识 |
| `drugCode` | `string` | 院内药品目录编码 |
| `drugName` | `string` | 通用名，商品名另设字段 |
| `specification` | `string/null` | 规格未返回时必须为 `null` |
| `dose` | `object` | `value:number/null`、`unit:string/null`、`status:enum` |
| `frequency` | `object` | 频次结构化值；未知不得填正常值 |
| `route` | `object` | `code/name/status` |
| `duration` | `object` | `value/unit/status` |
| `editableFields` | `string[]` | 后端明确允许医生修改的字段 |
| `sourceRefs` | `string[]` | 规则、目录、说明书或证据引用 |

推荐状态枚举：

```text
confirmed
pending_rule_confirmation
pending_doctor_confirmation
missing
not_applicable
```

## 8. 医生决策接口

### 8.1 请求

```http
POST /api/recommendations/REC-E001-v3/decision
Content-Type: application/json
Authorization: Bearer <access-token>
Idempotency-Key: 6f5c2b15-79d2-4c4d-a7d8-8a6f8e0f0001
If-Match: recommendation-v1
```

```json
{
  "action": "modify",
  "candidateId": "C-CEF-AZI",
  "recommendationVersion": 1,
  "reason": "根据患者当前用药和检验结果调整给药途径，保留方案适用性",
  "modifiedPrescription": {
    "medications": [
      {
        "medicationId": "MED-C-CEF-AZI-01",
        "changes": [
          { "field": "route", "before": null, "after": { "code": "IV", "name": "静脉" } },
          { "field": "frequency", "before": null, "after": { "value": 1, "unit": "per_day" } }
        ]
      }
    ]
  },
  "riskHandling": {
    "acknowledgedAlertIds": ["HR-XDEPT-001"],
    "missingInfoDisposition": "requires_follow_up"
  }
}
```

兼容现有前端字段：后端当前可继续接收 `modifiedRegimen:string`，但正式实现结构化处方表格时必须优先支持 `modifiedPrescription`。两者同时存在时，以结构化字段为准，并在审计中保存修改前后差异。

`action` 取值：

| 值 | 行为 |
|---|---|
| `adopt` | 采纳候选，创建处方草稿 |
| `modify` | 保存医生修改后的结构化处方，创建处方草稿 |
| `reject` | 保存驳回原因，不创建处方草稿 |

### 8.2 响应

```json
{
  "decisionId": "DEC-20260810-0001",
  "action": "modify",
  "recommendationId": "REC-E001-v3",
  "prescriptionDraftId": "DRAFT-20260810-0001",
  "draftStatus": "created",
  "recommendationStatus": "decided",
  "pharmacistReviewId": "REV-20260810-0001",
  "blocked": false,
  "auditEventIds": ["AUD-20260810-0001", "AUD-20260810-0002"],
  "traceId": "trc-20260810-000001"
}
```

后端必须执行：

1. 校验患者、就诊、推荐版本仍然有效。
2. 重新执行硬规则，不能信任前端传入的 `canAdopt`。
3. 阻断候选不能 `adopt` 或 `modify`，只能 `reject` 或返回处理错误。
4. 校验药品必须来自当前有效院内目录。
5. 校验所有修改字段是否在 `editableFields` 内。
6. 保存原推荐、修改前后差异、处理原因、操作人、时间、规则命中和审计事件。
7. 只创建处方草稿，不写正式医嘱。
8. 使用 `Idempotency-Key` 防止重复点击创建多个决策或草稿。

## 10. 前端对接状态

当前前端已直接使用：

```text
GET  /api/worklist
GET  /api/workbench/{encounterId}
POST /api/recommendations/{recommendationId}/decision
```

当前前端类型中 `CandidatePlan` 仍主要使用 `regimen:string`、`drugCodes:string[]`。为了支持规范化处方表格，后端响应必须补齐 `medications[]`、结构化剂量/频次/途径/疗程和 `sourceRefs`；在此之前，前端只能显示“待规则确认”，不得从自然语言推算具体数值。

## 11. 测试方案

### 11.1 契约测试

使用 OpenAPI/JSON Schema 对以下内容校验：

- 成功响应字段完整性和类型。
- `date-time`、枚举、必填字段、数组唯一标识。
- `dose.value`、`frequency.value`、`duration.value` 为未知时必须是 `null`，不能伪造为 `0`。
- `candidate.medications[].drugCode` 必须存在于院内目录。
- 阻断候选与 `canAdopt` 状态一致。
- 错误响应统一包含 `code/message/traceId`。

### 11.2 Core API 集成测试

| 场景 | 前置数据 | 预期 |
|---|---|---|
| 普通 CAP | 无过敏、关键检验完整 | 返回首选和备用方案，医生可采纳 |
| 已确认过敏 | 跨就诊过敏事实 | 对应候选 `blocked=true`，采纳返回 `422/409` |
| 严重 ADR | 已确认严重不良反应 | 强提醒或阻断状态准确返回 |
| 跨科室冲突 | 当前有效用药来自其他科室 | 返回冲突事实和处理要求 |
| 关键检验缺失 | 肌酐/CRP 缺失 | `missingStatus=missing`，不能当作正常值 |
| 旧版本提交 | 推荐版本已过期 | 返回 `409`，不能覆盖新推荐 |
| 重复提交 | 相同 `Idempotency-Key` 重复请求 | 返回同一 `decisionId/draftId` |
| 权限越界 | 医生访问非负责科室 | 返回 `403`，不泄露患者内容 |
| 阻断绕过 | 修改请求伪造 `riskHandling` | 后端仍拒绝非驳回提交 |
| 药品目录失效 | 候选药品已停用 | 不生成草稿，返回目录校验错误 |

## 12. 联调验收标准

- 前端不再依赖固定药品、固定剂量或固定风险文案。
- 首选方案的药品、用法用量、频次、途径、疗程均来自结构化后端字段或明确显示待确认。
- 所有硬规则由后端复算并不可绕过。
- 医生修改能够保存字段级差异、处理原因、操作人、版本和审计事件。
- 采纳后只生成处方草稿，`formalOrderCreated=false`。
- 普通、过敏、严重 ADR、跨科室冲突、关键检验缺失、版本冲突和接口降级场景均有自动化测试。
- API 响应、数据库决策记录、处方草稿记录和审计事件可以通过 `decisionId/draftId/traceId` 互相追溯。
