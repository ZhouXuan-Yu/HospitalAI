# 处方审核前后端接口契约

**文档版本**：`v1.0`  
**契约标识**：`hospitalai.pharmacist-review.v2`  
**适用页面**：药师工作台 / 处方审核  
**状态**：前端对接基线，后端实现前须经过接口评审  
**更新时间**：2026-08-10

## 1. 目标与业务边界

处方审核页面服务药师对**指定科室、指定审核日**的未审核医嘱进行审核。工作范围是科室，不是患者列表；患者仅作为医嘱和联合用药审查的上下文。

页面的最小业务闭环为：

```text
选择药师负责科室
  -> 选择审核日
  -> 拉取该科室当日未审核医嘱
  -> 系统自动完成单医嘱审查和当日联合用药审查
  -> 药师点击某一行
  -> 加载该患者当日全部有效医嘱及规则依据
  -> 药师通过、提出疑问或退回
  -> 保存审核结果与审计事件
```

本接口不创建正式医嘱，不改变医生处方内容，不以客户端传入的患者、药师或权限字段作为可信来源。正式身份、科室权限、规则执行和审计均由后端负责。

### 1.1 页面展示口径

| 口径 | 要求 |
|---|---|
| 主列表粒度 | 一行代表一条药品医嘱，不是一位患者 |
| 主列表范围 | 当前药师有权限的一个科室、一个审核日、未审核医嘱 |
| 单医嘱审查 | 检查该药品、剂量/频次/途径、患者事实和规则依据 |
| 联合用药审查 | 检查同一患者、同一就诊、同一审核日内全部有效医嘱；可包含其他科室开立的当日医嘱 |
| 历史医嘱 | 不作为当日联合用药清单；历史过敏和严重不良反应作为患者安全事实继续提示 |
| 长期医嘱 | 只要在审核日有效且未停用，每天生成当天待审记录 |
| 右侧详情 | 初始不展开；用户点击列表行或“查看”后请求详情并展开 |
| 审核结果 | `approved` 通过、`question` 有疑问、`returned` 退回；硬阻断不得通过 |

### 1.2 审核日和时区

- `reviewDate` 使用医院业务时区的自然日，格式为 `YYYY-MM-DD`。
- 默认时区为 `Asia/Shanghai`，生产环境由医院配置覆盖。
- “当日医嘱”按医嘱在该业务日处于有效状态判定，不按浏览器本地时区判定。
- 同一长期医嘱每天的审核任务是有意重复产生的业务记录，不属于重复数据。

## 2. 认证、权限与通用约定

### 2.1 认证

```http
Authorization: Bearer <OIDC access token>
Content-Type: application/json
Accept: application/json
X-Request-Id: <client-generated-uuid>
```

开发环境可以使用模拟身份，但模拟身份只能由后端配置注入，不能由前端通过请求体伪造。当前前端开发角色为 `pharmacist`。

### 2.2 角色权限

| 角色 | 权限 |
|---|---|
| 药师 | 读取本人负责科室的审核队列、查看有权限患者的当日上下文、提交审核结果 |
| 医生 | 不调用本组药师审核提交接口；医生处方推荐使用医生工作台接口 |
| 管理员 | 可查看配置范围内队列和审计，但不能替代原药师提交审核 |
| 开发环境超级管理员 | 可查看调试信息，但不能绕过硬阻断、伪造审核人或删除审计记录 |

后端必须在每个接口重新校验 `departmentId` 与当前登录人的负责范围。未授权科室返回 `403`，不能通过修改 URL 访问其他科室。

### 2.3 通用响应和错误格式

成功响应直接返回接口定义的 JSON 对象；错误统一返回：

```json
{
  "code": "PHARMACIST_REVIEW_FORBIDDEN",
  "message": "当前药师无权访问该科室审核队列",
  "requestId": "req-20260810-000001",
  "details": []
}
```

通用错误码：

| HTTP | `code` | 前端处理 |
|---:|---|---|
| 400 | `INVALID_PARAMETER` | 显示参数错误并保留当前筛选条件 |
| 401 | `UNAUTHENTICATED` | 重新认证 |
| 403 | `PHARMACIST_REVIEW_FORBIDDEN` | 显示无权限，不重试 |
| 404 | `REVIEW_NOT_FOUND` | 刷新列表并提示记录已不存在 |
| 409 | `REVIEW_ALREADY_RESOLVED` | 刷新该行，提示已被其他药师处理 |
| 422 | `REVIEW_HARD_BLOCKED` | 禁止提交通过，展示阻断规则 |
| 429 | `RATE_LIMITED` | 按 `Retry-After` 延迟重试 |
| 500/503 | `REVIEW_SERVICE_UNAVAILABLE` | 显示服务异常，不伪造审核成功 |

## 3. 数据类型定义

以下类型为前后端共享模型。字段类型使用 TypeScript 表示，JSON 传输使用对应的 JSON 基本类型。

```ts
type ISODate = string // YYYY-MM-DD
type ISODateTime = string // RFC 3339，例如 2026-08-10T09:30:00+08:00
type UUID = string

type ReviewStatus = 'unreviewed' | 'approved' | 'question' | 'returned'
type ReviewResult = 'auto_passed' | 'needs_pharmacist_review' | 'blocked' | 'insufficient_data'
type ReviewLevel = 'normal' | 'attention' | 'strong' | 'blocked'
type RuleSeverity = 'info' | 'attention' | 'strong' | 'block'
type RuleCategory = 'single_order' | 'combination' | 'patient_safety' | 'data_quality'
```

### 3.1 患者与就诊

```ts
interface PatientSummary {
  patientId: string
  displayName: string
  displayNameMask?: string
  sex: 'male' | 'female' | 'unknown'
  age?: number
  encounterId: string
  diagnosis?: string
  admissionAt?: ISODateTime
}
```

生产环境中 `displayName` 必须遵守医院脱敏策略。前端不可自行拼接身份证号、手机号等身份信息。

### 3.2 药品医嘱

```ts
interface MedicationOrder {
  orderId: string
  drug: {
    drugCode: string
    genericName: string
    brandName?: string
    strength?: string
    dosageForm?: string
  }
  dose?: number
  doseUnit?: string
  frequency?: string
  route?: string
  startAt: ISODateTime
  endAt?: ISODateTime | null
  status: 'active' | 'stopped' | 'cancelled' | 'completed'
  isLongTerm: boolean
  orderDepartment: { departmentId: string; departmentName: string }
  orderedBy?: { userId: string; displayName: string }
  orderedAt: ISODateTime
  sourceSystem: 'his_adapter' | 'preview_fixture'
}
```

当日有效判定：

```text
status = active
且 startAt <= reviewDate 23:59:59
且 endAt 为空或 reviewDate <= endAt 所在业务日
```

已停止、已取消、已完成的医嘱不得进入当日有效联合用药集合。长期医嘱只要满足上述条件，就应在每个有效日产生一个 `dailyReviewId`。

### 3.3 规则命中和事实引用

```ts
interface FactReference {
  factType: 'allergy' | 'adverse_drug_reaction' | 'lab' | 'diagnosis' | 'medication_order'
  factId: string
  label: string
  observedAt?: ISODateTime
  sourceSystem: string
}

interface RuleHit {
  ruleId: string
  ruleVersion: string
  ruleName: string
  category: RuleCategory
  severity: RuleSeverity
  message: string
  blocking: boolean
  facts: FactReference[]
  evidenceRefs?: Array<{
    evidenceId: string
    title: string
    locator?: string
    reviewStatus: 'approved' | 'demo_unpublished'
  }>
}
```

`facts` 必须指向可追溯的结构化事实；“未知”不能被规则引擎当作“正常”。演示证据必须显示 `demo_unpublished`，不能伪装成医院正式依据。

### 3.4 每日医嘱审核项

```ts
interface DailyMedicationReviewItem {
  dailyReviewId: string
  orderId: string
  reviewDate: ISODate
  departmentId: string
  status: ReviewStatus
  patient: PatientSummary
  order: MedicationOrder
  singleOrderReview: {
    result: ReviewResult
    level: ReviewLevel
    summary: string
    ruleHits: RuleHit[]
  }
  combinationReview: {
    scope: {
      samePatient: true
      sameEncounter: true
      sameReviewDate: true
      includesOtherDepartments: true
      includedOrderIds: string[]
    }
    result: ReviewResult
    level: ReviewLevel
    summary: string
    conflicts: Array<{
      conflictId: string
      conflictType: 'duplicate_class' | 'interaction' | 'compatibility' | 'duplicate_ingredient'
      involvedOrderIds: string[]
      message: string
      severity: RuleSeverity
      ruleId: string
    }>
    ruleHits: RuleHit[]
  }
  overallReview: {
    result: ReviewResult
    level: ReviewLevel
    summary: string
    blocking: boolean
  }
  createdAt: ISODateTime
  resolvedAt?: ISODateTime | null
}
```

## 4. 接口清单

| 方法 | 路径 | 必须性 | 页面用途 |
|---|---|---|---|
| `GET` | `/api/pharmacist/departments` | 推荐 | 获取当前药师负责的科室和待审数量 |
| `GET` | `/api/pharmacist/reviews` | 必须 | 获取科室/日期下的医嘱审核表格 |
| `GET` | `/api/pharmacist/reviews/{dailyReviewId}` | 必须 | 点击一行后加载右侧详细审核上下文 |
| `POST` | `/api/pharmacist/reviews/{dailyReviewId}/resolve` | 必须 | 提交药师审核结论和审计信息 |

### 6.1 列表接口实现要求

1. `items` 必须按医嘱返回，不能仅返回患者聚合对象。
2. 同一患者当天有三条有效医嘱，列表应有三行；每行都携带相同患者摘要和自己的 `orderId`。
3. 联合用药结果可以在每一行重复返回，前端据此直接展示异常标记；详情接口返回完整清单。
4. `onlyAbnormal=true` 只过滤列表，不改变规则计算范围。计算范围仍应包含该患者当天全部有效医嘱。
5. `status=unreviewed` 只返回尚未形成最终药师结论的每日审核记录。
6. 数据为空时返回 `200`、空数组和完整 `summary`，不能返回 `404`。

## 8. 提交药师审核结论

### `POST /api/pharmacist/reviews/{dailyReviewId}/resolve`

#### 请求体

```json
{
  "schemaVersion": "hospitalai.pharmacist-review-resolution.v1",
  "decision": "approved",
  "note": "已核对同日医嘱，结合患者当前用药情况通过审核",
  "acknowledgedRuleIds": ["RX-COMB-001"],
  "followUp": {
    "action": "monitor",
    "expectedAt": "2026-08-11T09:00:00+08:00"
  },
  "clientRequestId": "6b4d7d09-8a33-4e45-b6d7-7e4c28c98001"
}
```

字段规则：

| 字段 | JSON 类型 | 必填 | 规则 |
|---|---|---:|---|
| `schemaVersion` | `string` | 是 | 必须为当前版本 |
| `decision` | `string` | 是 | `approved` / `question` / `returned` |
| `note` | `string` | 是 | 说明审核判断；长度 1-2000 |
| `acknowledgedRuleIds` | `string[]` | 否 | 仅能确认服务端返回的规则 ID |
| `followUp` | `object|null` | 否 | 有疑问或需监测时可填写 |
| `clientRequestId` | `string` | 是 | UUID，用于幂等提交 |

服务端禁止客户端传入或覆盖 `operatorId`、`operatorRole`、`resolvedAt`、`auditEventId`、`departmentId`。这些字段从认证上下文和服务端时钟生成。


### 8.1 提交约束

- `overallReview.blocking=true` 或存在 `severity=block` 的未处理命中时，`decision=approved` 必须返回 `422 PHARMACIST_REVIEW_HARD_BLOCKED`。
- `question` 和 `returned` 必须要求非空 `note`，并写入待跟进状态。
- 已处理记录再次提交返回 `409`，不能覆盖已有审核结论。
- 同一 `clientRequestId` 重试应返回第一次成功结果，不产生第二条审核事件。
- 每次成功提交都生成不可删除的审计事件，至少包含每日审核 ID、医嘱 ID、患者/就诊 ID、操作人、角色、时间、决策、规则 ID、备注和请求 ID。

## 9. 前端调用时序

```text
进入处方审核页
  -> GET /departments
  -> 默认选择第一个有权限科室
  -> GET /reviews?departmentId=...&reviewDate=...&status=unreviewed
  -> 渲染表格，不请求右侧详情

点击某行
  -> GET /reviews/{dailyReviewId}
  -> 展开右侧详情

点击通过/有疑问/退回
  -> POST /reviews/{dailyReviewId}/resolve
  -> 成功后刷新当前行和统计数
  -> 失败时保留详情、显示服务端错误，不显示成功
```

前端必须处理加载中、空数据、接口失败、权限不足、并发冲突、硬阻断和重复提交状态。右侧详情关闭后不应清空科室、日期、搜索和异常筛选。

## 10. JSON Schema、OpenAPI 与兼容策略

1. 后端应提供 OpenAPI 3.1 文档，路径和字段以本文件为业务基线。
2. `DailyMedicationReviewItem`、详情响应和审核请求分别生成 JSON Schema，前端使用 AJV 或等价校验进行契约测试。
3. 生产接口禁止使用 `drugs: "药品A · 药品B"` 这类拼接字段；药品必须是结构化对象或数组。
4. 现有 `GET /api/pharmacist/reviews` 的旧版摘要模型可以在迁移期间由适配层转换，但不能作为长期契约。转换不得丢失 `orderId`、`reviewDate`、单项审查、联合审查和规则命中。
5. 版本升级采用新 `schemaVersion`，新增可选字段向后兼容；删除或改变字段含义必须发布新版本。

## 11. 测试数据导入与测试边界

### 11.1 数据来源

- 生产：HIS 适配器提供真实结构化数据，后端落库并执行规则。
- 前端开发调试：允许导入版本化 JSON fixture，仅用于验证页面交互，必须显示“合成模拟数据”。
- 模拟数据不得被称为真实临床证据，不得进入正式规则和科研结论。
- 建议 fixture 文件命名：`hospitalai.pharmacist-review.v2.normal.json`、`...conflict.json`、`...long-term.json`。

### 11.2 必测场景

| 编号 | 场景 | 预期 |
|---|---|---|
| T01 | 一个科室两名患者、各一条正常医嘱 | 表格两行，单医嘱自动通过 |
| T02 | 同一患者当天 A/B 两条同类医嘱 | 表格两行，每行显示联合异常；详情包含 A/B |
| T03 | A 医嘱昨日结束，B 医嘱今日有效 | 联合清单只包含 B，不误报历史冲突 |
| T04 | 长期医嘱开始且未停用 | 每个有效日均出现新的 `dailyReviewId` |
| T05 | 长期医嘱已停用 | 停用日及之后不再进入待审核队列 |
| T06 | 另一科室当日有同一患者医嘱 | 主列表按选中科室过滤；详情联合审查包含该医嘱 |
| T07 | 已确认过敏或严重不良反应 | 命中硬阻断；提交通过返回 `422` |
| T08 | 关键检验缺失 | 返回 `insufficient_data`，未知不当作正常 |
| T09 | 两名药师同时处理 | 后提交者收到 `409`，已有结论不被覆盖 |
| T10 | 接口 503 或 AI/知识服务不可用 | 患者和基础队列可显示；不得伪造自动通过 |
| T11 | 未授权科室 URL 访问 | `403`，不泄露患者或医嘱数据 |
| T12 | 重复提交同一 `clientRequestId` | 返回同一结果，只生成一条审计事件 |

## 13. 安全、审计与数据一致性验收

- 服务端从 Token 获取药师身份和科室范围，拒绝客户端伪造身份、科室和审核时间。
- 患者标识、医嘱标识和规则命中在日志中按医院隐私策略脱敏。
- 审核提交使用幂等键，避免网络重试产生重复决策。
- 规则快照、规则版本、输入事实版本和审核结论必须可追溯。
- 审计记录只追加，不允许前端删除或修改。
- 发生 HIS 数据版本冲突时返回 `409` 或明确的数据版本错误，不静默覆盖。
- 前端不得把“自动审核通过”直接等同于药师审核通过；两者必须分别展示。
- 知识库不可用时，后端应明确返回降级状态；不能以空规则结果伪装为安全通过。
