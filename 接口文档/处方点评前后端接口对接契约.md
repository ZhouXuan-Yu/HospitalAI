# 处方点评前后端接口对接契约

> 文档版本：`v1.0.0`  
> 适用页面：`/pharmacy/retrospective`  
> 前端实现：`apps/web/src/views/PharmacyWorkbench.vue`  
> 预览数据：`apps/web/src/data/retrospective-review.json`（仅前端验证，不作为生产数据）

## 1. 目标与边界

处方点评页面用于药师对**患者出院后的历史医院医嘱和自购药记录**进行回顾性用药合理性分析。后端必须返回可追溯的原始记录、来源和证据，前端只负责展示、筛选、展开详情和提交药师操作。

本接口不做以下事情：

- 不自动诊断，不自动开方，不把模型生成文字作为医学事实。
- 不根据缺失字段推测合理性；缺失时只能返回 `insufficient`。
- 不把“疑似不合理”直接改成停药、禁用或正式医嘱。
- 不把自购药记录当作医院正式医嘱；两者必须保留不同来源。
- 不把 `P < 0.05` 单独解释成“某药适合某类患者”。统计结果必须同时带样本量、效应量、置信区间、混杂因素和审核状态。

## 2. 业务流程

```text
药师打开处方点评
  -> 查询可点评患者
  -> 选择患者和出院后时间范围
  -> 读取医院全部历史医嘱 + 自购药记录 + 诊断/结局/关键安全事实
  -> 后端按六个维度执行确定性规则
  -> 前端展示逐条结论
  -> 点击单条记录，读取右侧证据详情
  -> 点击“生成点评报告”
  -> 后端生成结构化报告草稿
  -> 药师审阅、补充意见或确认
  -> 保存点评版本和审计事件
```

六个必评维度：

| 编码 | 维度 | 允许结论 |
|---|---|---|
| `indication_match` | 适应证是否匹配 | `reasonable` / `suspected_unreasonable` / `insufficient` |
| `dose_regimen` | 用法用量是否合理 | 同上 |
| `duplicate_therapy` | 是否重复用药 | 同上 |
| `drug_interaction` | 是否存在药物相互作用 | 同上 |
| `contraindication_precaution` | 是否存在禁忌或慎用情形 | 同上 |
| `course_stop_timing` | 疗程和停药时机是否恰当 | 同上 |

## 3. 通用约定

### 3.1 基础信息

| 项目 | 约定 |
|---|---|
| Base URL | `/api` |
| Content-Type | `application/json` |
| 字符集 | UTF-8 |
| 时间 | ISO-8601，带时区，例如 `2026-08-10T09:30:00+08:00` |
| 日期 | `YYYY-MM-DD` |
| ID | 后端生成的不可变字符串，不使用患者姓名作为 ID |
| 分页 | `page` 从 1 开始，`pageSize` 最大 100 |
| 幂等 | 所有写接口要求 `Idempotency-Key` 请求头 |
| 并发 | 写接口要求 `If-Match` 或 `version`，禁止静默覆盖 |

### 3.2 权限

| 操作 | 医生 | 药师 | 研究人员 | 管理员 |
|---|---:|---:|---:|---:|
| 查看本人授权范围患者 | 否 | 是 | 按脱敏权限 | 按授权 |
| 查看医院医嘱和自购药 | 否 | 是 | 仅脱敏研究数据 | 按授权 |
| 生成点评分析 | 否 | 是 | 否，除非使用脱敏队列 | 按授权 |
| 保存药师点评 | 否 | 是 | 否 | 按授权 |
| 导出包含患者级数据 | 否 | 按医院授权 | 不允许直接导出身份信息 | 按审计授权 |

后端必须以服务端权限为准，不能信任前端传入的 `departmentId`、`reviewerId` 或 `patientId`。所有查询和写入都必须生成审计事件。

## 4. P0 接口清单

| 方法 | 路径 | 用途 | 前端触发 |
|---|---|---|---|
| `GET` | `/pharmacy/retrospective/patients` | 查询药师可点评的患者 | 打开页面、筛选患者 |
| `GET` | `/pharmacy/retrospective/patients/{patientId}/workspace` | 读取点评工作区及全部原始记录 | 选择患者 |
| `GET` | `/pharmacy/retrospective/medications/{medicationRecordId}` | 读取单条药物完整证据 | 点击表格行 |
| `POST` | `/pharmacy/retrospective/analyses` | 创建一次点评分析任务 | 点击“生成点评报告” |
| `GET` | `/pharmacy/retrospective/analyses/{analysisId}` | 查询分析状态和报告结果 | 轮询或刷新页面 |
| `POST` | `/pharmacy/retrospective/analyses/{analysisId}/review` | 保存药师审阅、修订和确认 | 保存药师意见 |
| `GET` | `/pharmacy/retrospective/analyses/{analysisId}/audit-events` | 查看本次分析审计轨迹 | 审计入口 |

P1 接口（报告导出和研究沉淀）在 P0 工作区完成后实现：

| 方法 | 路径 | 用途 |
|---|---|---|
| `POST` | `/pharmacy/retrospective/analyses/{analysisId}/exports` | 创建报告/数据支撑包导出任务 |
| `GET` | `/pharmacy/retrospective/exports/{exportId}` | 查询 ZIP、报告和 manifest 的生成状态 |

### 5.4 创建点评分析任务

```http
POST /api/pharmacy/retrospective/analyses
Idempotency-Key: RETRO-ANALYSIS-RW-2026-0001-V3
If-Match: "3"
Content-Type: application/json
```

请求体：

```json
{
  "workspaceId": "RW-2026-0001",
  "workspaceVersion": 3,
  "analysisDimensions": [
    "indication_match",
    "dose_regimen",
    "duplicate_therapy",
    "drug_interaction",
    "contraindication_precaution",
    "course_stop_timing"
  ],
  "ruleSetVersion": "pharmacy-retrospective-rules.v1",
  "evidencePolicy": "reviewed_or_explicitly_unpublished",
  "requestedBy": "由服务端从登录身份取得，不接受前端覆盖"
}
```

响应：

- `202 Accepted`：任务已入队，返回 `analysisId`，前端读取状态。
- `200 OK`：开发环境允许同步完成时返回完整结果，但仍必须保存任务和审计记录。
- `409 Conflict`：工作区版本已变化，前端必须重新读取，禁止覆盖。

```json
{
  "analysisId": "AN-2026-0001",
  "workspaceId": "RW-2026-0001",
  "status": "queued",
  "requestedAt": "2026-08-10T10:00:00+08:00",
  "traceId": "TRACE-RETRO-0001"
}
```

分析状态：`queued -> running -> succeeded`，异常时为 `failed`，部分数据可用但某些规则服务失败时为 `partial`。`partial` 不能显示为完整点评完成。

## 6. 字段和状态规则

### 6.1 来源枚举

| 值 | 含义 |
|---|---|
| `hospital_order` | HIS 医院医嘱 |
| `self_purchased` | 患者或家属自购/自行服用记录 |
| `patient_interview` | 患者访谈原始记录，仅作为证据来源，不等同医嘱 |
| `discharge_medication` | 出院带药清单 |

### 6.2 结论枚举

- `reasonable`：提供的事实足以支持当前维度结论，必须带依据。
- `suspected_unreasonable`：规则或证据发现需要处理的问题，但不等同最终医学否定。
- `insufficient`：关键字段缺失、来源未审核、记录冲突或不能支持判断。

### 6.3 数据质量

后端必须将以下情况写入 `missingFields` 或 `conflictFields`：

- 药品只有商品名，没有通用名、规格或药品编码。
- 医嘱缺少剂量、频次、途径、开始时间或结束时间。
- 自购药没有购药记录、患者确认或实际服用时间。
- 诊断、肝肾功能、过敏史等判断所需事实缺失。
- 同一来源记录重复、版本过旧或不同来源互相冲突。

这些情况不能被后端序列化为空字符串后丢失，也不能默认当作正常。

## 7. 错误响应

统一格式：

```json
{
  "error": {
    "code": "RETRO_WORKSPACE_VERSION_CONFLICT",
    "message": "点评工作区已更新，请重新读取后提交。",
    "fieldErrors": [],
    "requestId": "REQ-RETRO-0001",
    "traceId": "TRACE-RETRO-0001"
  }
}
```

| HTTP | 错误码示例 | 前端处理 |
|---:|---|---|
| `400` | `INVALID_DATE_RANGE` | 标记参数错误，不提交 |
| `401` | `UNAUTHENTICATED` | 跳转登录并清除可编辑状态 |
| `403` | `RETRO_SCOPE_FORBIDDEN` | 显示无权访问该患者或科室 |
| `404` | `PATIENT_NOT_FOUND` / `ANALYSIS_NOT_FOUND` | 显示记录不存在，不使用本地替代 |
| `409` | `RETRO_WORKSPACE_VERSION_CONFLICT` | 重新读取，展示版本差异，禁止静默覆盖 |
| `422` | `RETRO_INVALID_REVIEW` | 显示字段级错误和缺失依据 |
| `429` | `ANALYSIS_RATE_LIMITED` | 显示稍后重试，不重复创建任务 |
| `500` | `RETRO_INTERNAL_ERROR` | 显示失败并保留可读原始事实 |
| `503/504` | `RETRO_ANALYSIS_UNAVAILABLE` | 显示服务降级；不能伪造点评结论 |

### 9.3 安全测试

- 医生访问未授权患者返回 `403`，不能通过修改 URL 越权。
- 药师只能访问被授权科室和患者范围。
- 前端传入其他 `reviewerId` 不得改变服务端操作人。
- 导出接口不能通过 `uri`、文件名或路径穿越读取任意文件。
- 证据原文不得被未授权角色下载。
- 审计接口禁止删除、更新历史事件。
- 对药品名称、证据片段、患者自述文本进行 XSS/HTML 注入测试。
- 日志中禁止写入身份证号、手机号和完整患者姓名。

### 9.4 性能和一致性测试

| 指标 | P0 目标 |
