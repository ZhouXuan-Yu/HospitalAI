# 药历页面后端对接接口与测试说明

> 文档版本：v1.0
> 
> 对应前端页面：`/pharmacy/records`
> 
> 对应前端组件：`apps/web/src/views/PharmacyWorkbench.vue`
> 
> 文档用途：为后端实现药历候选患者、患者事实自动导入、药师药历草稿、住院用药变更、查房沟通、医生处理结果和 Word/PDF 导出提供统一接口契约。

## 1. 业务边界

药历不是所有患者的全量病历，也不是医生病历的替代品。它由临床药师主动选择病情较重、用药复杂或存在特殊用药问题的少数患者建立，用于记录患者家庭用药、住院期间药品变化、药师分析建议以及与医生查房沟通的处理结果。

系统必须遵守以下边界：

1. 患者和就诊信息由后端统一模型提供，前端不得自行拼接或修改原始事实。
2. 过敏、不良反应、诊断、医嘱、检验等事实必须保留来源、来源标识、采集时间、数据版本和缺失状态。
3. 药师可以建立药历、补充访谈、添加药品变更和填写建议，但不能通过药历接口直接生成正式医嘱。
4. 医生的处理结果只记录“采纳、修改后执行、不采纳、暂不处理”等沟通结果，正式医嘱仍由医院医嘱系统完成。
5. 药历建立应支持收费状态记录，但不能因为保存草稿自动计费。
6. 所有新增、修改、提交、医生处理和导出操作必须写入审计日志。
7. 前端验证环境可以使用 `hospitalai.frontend-flow.v1` 合成场景；生产接口不得返回内置合成患者作为真实数据。

## 2. 角色与权限

| 角色 | 允许操作 | 禁止操作 |
|---|---|---|
| 临床药师 | 查看负责科室候选患者；建立药历；填写访谈、病史补充、药品变更、方案分析和药师建议；保存草稿；提交医生沟通；导出 | 修改系统原始事实；确认正式医嘱；绕过权限访问其他科室患者 |
| 医生 | 查看关联药历；查看自动导入事实和药师建议；填写沟通处理结果 | 修改药师原始访谈记录；伪造药师身份；通过药历接口直接发布正式医嘱 |
| 药学负责人 | 查看本科室药历和完成进度；审核药历；查看收费核对状态 | 删除审计记录；替代医生生成正式医嘱 |
| 管理员 | 配置月度目标、权限和导出策略；查询审计 | 修改临床事实、伪造审核人、绕过业务状态 |
| 开发验证角色 | 仅在 `VITE_UI_PREVIEW=true` 环境使用合成 JSON 场景验证前端 | 访问真实患者数据；调用生产写接口 |

建议所有接口从认证上下文获取 `operatorId`、`operatorRole`、`departmentScope`，不要信任前端提交的操作人字段。

## 3. 统一接口约定

### 3.1 基础路径

```text
/api/pharmacy/medication-records
```

生产环境必须通过医院 SSO/OIDC 认证。开发环境可以使用可替换的模拟身份，但响应中必须标记 `environment`，不得伪装成真实医院用户。

### 3.2 请求头

```http
Authorization: Bearer <access-token>
X-Request-Id: 8c2a9b5e-4b0e-4d1e-9c1a-001
Content-Type: application/json
If-Match: "record-version-3"
```

- `Authorization`：生产必填。
- `X-Request-Id`：链路追踪，后端没有收到时生成并在响应中返回。
- `If-Match`：保存草稿、修改事件和医生处理时用于乐观锁。
- 所有写接口必须支持幂等键，建议使用 `Idempotency-Key`。

### 3.3 成功响应

```json
{
  "requestId": "REQ-20260810-0001",
  "data": {},
  "meta": {
    "schemaVersion": "hospitalai.medication-record-api.v1",
    "serverTime": "2026-08-10T10:30:00+08:00",
    "environment": "production"
  }
}
```

### 3.4 错误响应

```json
{
  "requestId": "REQ-20260810-0002",
  "error": {
    "code": "RECORD_VERSION_CONFLICT",
    "message": "药历已被其他用户修改，请刷新后重试",
    "details": {
      "expectedVersion": 3,
      "currentVersion": 4
    }
  },
  "meta": {
    "schemaVersion": "hospitalai.medication-record-api.v1",
    "serverTime": "2026-08-10T10:31:00+08:00"
  }
}
```

建议状态码：

| 状态码 | 含义 |
|---|---|
| 200 | 查询或修改成功 |
| 201 | 创建成功 |
| 202 | 已接收异步导出任务 |
| 400 | 参数或 JSON Schema 校验失败 |
| 401 | 未认证 |
| 403 | 无权限或超出科室范围 |
| 404 | 患者、就诊或药历不存在 |
| 409 | 版本冲突、重复创建或状态冲突 |
| 422 | 临床业务校验不通过 |
| 429 | 频率限制 |
| 500 | 服务端异常 |

```text
RecordStatus:
  NONE, DRAFT, IN_PROGRESS, PENDING_PHYSICIAN,

  SEVERE_CONDITION              病情较重

  UNCLEAR_HOME_MEDICATION       家庭用药不清

  PENDING, ACCEPTED, MODIFIED, REJECTED, DEFERRED
```

## 6. 接口详细定义

### MR-01 获取重点患者候选列表

```http
GET /api/pharmacy/medication-records/candidates?departmentId=RESP&status=priority&page=1&pageSize=20
```

权限：临床药师、药学负责人、管理员。

筛选参数：

| 参数 | 类型 | 必填 | 说明 |
|---|---|---:|---|
| `departmentId` | string | 是 | 当前药师负责科室 |
| `status` | string | 否 | `priority`、`all`、`has_record` |
| `page` | integer | 否 | 默认 1 |
| `pageSize` | integer | 否 | 默认 20，最大 100 |

响应示例：

```json
{
  "requestId": "REQ-001",
  "data": {
    "items": [
```

响应示例：

```json
{
```

### MR-04 创建药历

```http
POST /api/pharmacy/medication-records
```

请求示例：

```json
{
  "encounterId": "E001",
  "selectionReason": "POLYPHARMACY",
  "interviewSource": "PATIENT",
  "patientConcern": "患者担心家庭用药与住院用药重复",
  "templateVersion": "medication-record-template.v1",
  "idempotencyKey": "CREATE-E001-PHARM-001"
}
```

服务端行为：

1. 校验操作人是否有该科室权限。
2. 校验 `encounterId` 当前有效且患者未被删除或脱敏策略禁止访问。
3. 拉取当前统一患者上下文并冻结 `sourceSnapshot`。
4. 同一 `encounterId` 已存在未取消药历时返回 `409 RECORD_ALREADY_EXISTS`，而不是重复创建。
5. 创建审计事件 `MEDICATION_RECORD_CREATED`。

响应至少包含：

```json
{
  "data": {
    "recordId": "MR-20260810-0001",
    "encounterId": "E001",
    "status": "DRAFT",
    "version": 1,
    "sourceSnapshotId": "SNAP-E001-003",
    "createdAt": "2026-08-10T09:00:00+08:00"
  }
}
```

### MR-06 保存药师药历草稿

```http
PATCH /api/pharmacy/medication-records/MR-20260810-0001/draft
```

请求示例：

```json
{
  "version": 2,
  "selectionReason": "POLYPHARMACY",
  "interviewSource": "PATIENT",
  "patientConcern": "患者担心家庭用药与住院用药重复",
  "historySummary": "患者既往有高血压史，家族史待补充",
  "homeMedicationStatus": "YES",
  "adherence": "OCCASIONAL",
  "homeMedicationNarrative": "患者口述药物名称、剂量、每日次数、服用时间及漏服情况",
  "analysis": "结合治疗目标、当前用药和病情变化进行分析",
  "recommendation": "建议与医生讨论调整方案并补充监测项",
  "saveAs": "IN_PROGRESS"
}
```

服务端必须：

- 只允许修改药师可编辑字段。
- 忽略或拒绝客户端提交的患者姓名、诊断、过敏、检验、医嘱等只读字段。
- 校验枚举、文本长度和敏感内容。
- 校验 `version`，版本不一致返回 409。
- 保存前后记录字段级差异，例如 `recommendation: null -> ...`。
- 保存草稿不触发正式医嘱，不自动改变医生处理状态。

响应：

```json
{
  "data": {
    "recordId": "MR-20260810-0001",
    "status": "IN_PROGRESS",
    "version": 3,
    "updatedAt": "2026-08-10T09:45:00+08:00",
    "auditEventId": "AUD-MR-0003"
  }
}
```

```http
POST /api/pharmacy/medication-records/MR-20260810-0001/medication-events
```

请求示例：

```json
{
  "eventDate": "2026-08-09",
  "eventType": "CHANGE",
  "drug": {
    "drugCode": "HOSP-0001",
    "drugName": "示例抗菌药",
    "strength": "500 mg",
    "form": "片剂"
  },
  "regimen": {
    "dose": 500,
    "doseUnit": "mg",
    "frequency": "BID",
    "route": "ORAL",
    "timing": "早餐后、晚餐后",
    "duration": "7 天"
  },
  "reason": "根据病情变化和查房沟通结果调整",
  "sourceOrderId": null,
  "version": 1
}
```

服务端自动补充 `eventId`、`source=PHARMACIST`、操作人、时间、审计事件和药历版本。系统从 HIS 自动导入的事件使用 `source=SYSTEM`，药师不能覆盖其原始内容。

### MR-08 / MR-09 修改或作废用药事件

```http
PATCH /api/pharmacy/medication-records/MR-20260810-0001/medication-events/ME-E001-0001
DELETE /api/pharmacy/medication-records/MR-20260810-0001/medication-events/ME-E001-0001
```

要求：

- `SYSTEM` 事件禁止直接修改和删除，必须通过数据更正流程产生新版本。
- `PHARMACIST` 事件可以修改，但必须提交事件版本。
- DELETE 只做逻辑作废，不能物理删除审计记录。
- 作废必须填写 `reason`，并记录原值和新状态。

### MR-10 保存医生查房处理结果

```http
POST /api/pharmacy/medication-records/MR-20260810-0001/physician-decision
```

请求示例：

```json
{
  "version": 3,
  "decision": "MODIFIED",
  "communicationDate": "2026-08-10",
  "communicationNote": "查房讨论后，医生根据病情变化调整方案并在正式医嘱系统执行",
  "formalOrderReference": "ORDER-20260810-0099"
}
```

业务规则：

| decision | 必填要求 | 药历状态 |
|---|---|---|
| `PENDING` | 不允许作为最终提交结果 | `PENDING_PHYSICIAN` |
| `ACCEPTED` | 必须有沟通日期和记录 | `ACCEPTED` |
| `MODIFIED` | 必须有沟通记录；正式医嘱引用可后补 | `MODIFIED` |
| `REJECTED` | 必须填写不采纳原因 | `REJECTED` |
| `DEFERRED` | 必须填写暂缓原因或后续时间 | `DEFERRED` |

该接口只记录医生对药师建议的处理结果，不创建正式医嘱。正式医嘱引用只能作为关联标识，不能由药历服务代替 HIS/CPOE 写入。

### MR-11 获取药历预览投影

```http
GET /api/pharmacy/medication-records/MR-20260810-0001/preview
```

## 8. 前端生产接入建议

当前验证环境使用 `flow.worklist` 和 `flow.getWorkbench(encounterId)`，并通过 `VITE_UI_PREVIEW=true` 控制验证场景。生产接入时建议新增 `medicationRecordApi.ts`，由页面状态层替换数据来源：

```text
GET  /candidates       -> recordPatients
GET  /context/{id}     -> selectedRecordWorkbench / autoImportedFacts
GET  /progress         -> 月度目标与计费侧栏
POST /                 -> createRecord
GET  /{recordId}       -> recordDraft + medicationEvents
PATCH /draft           -> saveRecord
POST /medication-events -> addMedicationEvent
POST /physician-decision -> 医生处理结果
GET  /export            -> Word/PDF 下载
```

前端需要处理：

1. `401`：跳转认证，不显示假患者数据。
2. `403`：显示无权限和科室范围，不允许通过切换参数绕过。
3. `404`：显示患者或药历不存在，并清空当前详情。
4. `409`：提示刷新，保留当前未提交内容，不能静默覆盖他人修改。
5. `422`：按字段展示后端业务校验错误。
6. API 失败时可以保留已经读取的患者事实，但必须显示“接口异常 / 数据时间”，不能把空值显示为正常。

## 9. JSON Schema 最低要求

后端应至少维护以下版本化 Schema：

```text
hospitalai.medication-record-candidate.v1.json
hospitalai.medication-record-context.v1.json
hospitalai.medication-record.v1.json
hospitalai.medication-record-preview.v1.json
hospitalai.medication-record-export.v1.json
```

Schema 必须约束：

- `patientId`、`encounterId`、`recordId` 的格式和非空规则；
- 所有枚举值；
- 日期必须为 ISO 8601 或 `YYYY-MM-DD`，不要混用本地格式；
- `dose` 为数值时必须同时有 `doseUnit`，不能把剂量拼在药品名字段中；
- `eventDate` 不得晚于当前日期，服务端时间作为最终判断；
- `physicianDecision` 与 `communicationNote` 的条件必填关系；
- 只读事实字段禁止出现在草稿写接口，或出现时必须拒绝；
- 文本长度、列表数量、分页上限和导出文件大小上限。

```powershell
.\gradlew test --tests '*MedicationRecord*'

```

契约测试至少覆盖：

2. MR-02 所有事实包含来源、来源标识、采集时间、数据版本和缺失状态。
3. MR-06 拒绝未知字段、非法枚举和只读事实修改。
4. MR-07 结构化药品、剂量、频次、途径和事件类型均可校验。

### 10.2 业务集成测试

以测试数据库和合成患者 `P001 / E001` 为例，完整链路：

```powershell
# 1. 查询候选患者
curl.exe -H "X-HospitalAI-Role: pharmacist" `
  "http://127.0.0.1:8080/api/pharmacy/medication-records/candidates?departmentId=RESP&status=priority"

# 2. 读取患者事实
curl.exe -H "X-HospitalAI-Role: pharmacist" `
  "http://127.0.0.1:8080/api/pharmacy/medication-records/context/E001"

# 3. 创建药历
curl.exe -X POST -H "Content-Type: application/json" `
  -H "X-HospitalAI-Role: pharmacist" `
  -H "Idempotency-Key: CREATE-E001-001" `
  -d '{"encounterId":"E001","selectionReason":"POLYPHARMACY","interviewSource":"PATIENT","templateVersion":"medication-record-template.v1"}' `
  "http://127.0.0.1:8080/api/pharmacy/medication-records"

# 4. 保存药师草稿
curl.exe -X PATCH -H "Content-Type: application/json" `
  -H "X-HospitalAI-Role: pharmacist" -H 'If-Match: "record-version-1"' `
  -d '{"version":1,"homeMedicationStatus":"YES","adherence":"OCCASIONAL","homeMedicationNarrative":"患者口述家庭用药","analysis":"待补充","recommendation":"建议查房沟通","saveAs":"IN_PROGRESS"}' `
  "http://127.0.0.1:8080/api/pharmacy/medication-records/MR-TEST-001/draft"

# 5. 新增药品变更
curl.exe -X POST -H "Content-Type: application/json" -H "X-HospitalAI-Role: pharmacist" `
  -d '{"eventDate":"2026-08-09","eventType":"CHANGE","drug":{"drugCode":"HOSP-0001","drugName":"示例抗菌药"},"regimen":{"dose":500,"doseUnit":"mg","frequency":"BID","route":"ORAL"},"reason":"查房沟通后调整"}' `
  "http://127.0.0.1:8080/api/pharmacy/medication-records/MR-TEST-001/medication-events"

# 6. 医生记录处理结果
curl.exe -X POST -H "Content-Type: application/json" -H "X-HospitalAI-Role: doctor" `
  -d '{"version":2,"decision":"MODIFIED","communicationDate":"2026-08-10","communicationNote":"医生修改后在正式医嘱系统执行"}' `
  "http://127.0.0.1:8080/api/pharmacy/medication-records/MR-TEST-001/physician-decision"

# 7. 导出 Word
curl.exe -L -H "X-HospitalAI-Role: pharmacist" `
  -o medication-record-test.docx `
  "http://127.0.0.1:8080/api/pharmacy/medication-records/MR-TEST-001/export?format=docx"

# 8. 导出 PDF
curl.exe -L -H "X-HospitalAI-Role: pharmacist" `
  -o medication-record-test.pdf `
  "http://127.0.0.1:8080/api/pharmacy/medication-records/MR-TEST-001/export?format=pdf"
```

每一步都要回读数据库或通过 MR-05/MR-13 验证：药历版本增加、状态正确、变更事件存在、医生处理结果和审计事件均已落库。

### 10.3 必测异常与边界场景

| 场景 | 预期结果 |
|---|---|
| 同一就诊重复创建药历 | 409，不创建第二条活动药历 |
| 药师访问其他科室患者 | 403，不返回患者事实 |
| 不存在的 `encounterId` | 404 |
| 保存时版本过期 | 409，不能覆盖他人修改 |
| 草稿提交未知字段 `allergyConfirmed` | 400 或 422，不能写入只读事实 |
| 系统导入事件被药师修改 | 403 或 422，必须走更正流程 |
| 医生选择 `REJECTED` 但没有原因 | 422 |
| 医生选择 `ACCEPTED` 但没有沟通日期 | 422 |
| 事件日期晚于当前服务端日期 | 422 |
| 关键事实缺失 | 正确返回 `missingInfo`，不能当作阴性或正常 |
| 导出未完成草稿 | 允许导出，但必须标记草稿和未完成 |
| 导出文件生成失败 | 返回明确错误，不生成空文件 |
| 重复提交同一 `Idempotency-Key` | 返回第一次结果，不重复写入 |
| 删除药师事件 | 逻辑作废，审计仍可查询 |
| 患者数据源版本变化 | 返回新快照提示，用户确认后刷新，不能静默覆盖药师填写内容 |

### 10.4 安全测试

1. 验证患者 IDOR：替换 `recordId`、`patientId`、`encounterId` 不能访问其他科室数据。
2. 验证角色越权：医生不能修改药师草稿，药师不能写医生处理结果，管理员不能删除审计。
3. 验证日志脱敏：应用日志和错误响应不得输出完整患者姓名、住院号、身份证号或联系方式。
4. 验证输入防护：文本字段防止 HTML、脚本、SQL 注入和超长 payload。
5. 验证导出权限：下载链接必须短期有效或实时鉴权，不能使用永久公开 URL。
6. 验证审计完整性：每个写接口、导出接口和权限拒绝都能关联 `requestId` 和操作者。
7. 验证硬规则边界：药历接口不能改变处方推荐硬阻断和正式医嘱状态。

### 10.5 性能与可靠性验收建议

| 指标 | 目标 |
|---|---:|
| 候选列表 P95 | <= 300 ms |
| 单患者上下文 P95 | <= 800 ms |
| 药历详情 P95 | <= 500 ms |
| 草稿保存 P95 | <= 500 ms |
| 事件写入 P95 | <= 500 ms |

## 11. 验收结论标准

后端接口只有同时满足以下条件，前端药历页面才可切换生产接口：

- MR-01 至 MR-10 已实现并通过契约、权限、异常和数据一致性测试；
- MR-02 的事实来源和缺失状态可追溯；
- MR-06、MR-07、MR-10 的状态和版本控制已落库；
- MR-12 能实际下载可打开的 Word 和 PDF 文件；
- MR-13 能回读完整审计链；
- 未实现的真实 HIS 字段必须明确返回缺失，不得用前端默认值伪造；
- 生产环境关闭 `VITE_UI_PREVIEW` 后，页面不再读取内置 `cap-full-flow.v1.json`；
- 端到端跑通“候选患者 → 自动导入 → 药师填写 → 保存 → 用药变更 → 医生处理 → 预览 → 导出”完整流程。
