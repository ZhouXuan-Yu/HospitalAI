# HospitalAI 商业级交付第一性原理与对标基准

文档版本：V0.4  
更新时间：2026-08-03  
状态：作为后续开发 MD 基线使用

## 1. 核心业务目标

HospitalAI 的商业价值不是“生成一个药品建议”，而是在医院真实诊疗链路中，把分散、异构、可变更的患者事实、药品目录、医学证据、硬规则、医生审核、药师复核、处方草稿回写和真实用药反馈连成可审计闭环。

本系统必须解决四个根问题：

1. 医生开方前无法快速得到完整、可信、跨就诊的用药安全上下文。
2. 历史确认过敏、严重不良反应、跨科室当前用药等高风险事实没有稳定进入本次决策。
3. 推荐理由和排除理由缺少证据定位、规则版本和审核状态，难以被医院正式采信。
4. 医生修改、药师复核、真实用药与结局没有形成可追溯的数据资产，无法支撑后续科研和知识沉淀。

## 2. 用户价值

- 临床医生：减少资料汇总时间，获得可比较候选方案和明确排除原因，同时保留最终决策权。
- 药师：把高风险处方、规则命中、证据来源和医生处理理由纳入统一复核队列。
- 科研负责人：从真实诊疗事件形成口径明确、版本冻结、可追溯的数据集和报告草稿。
- 信息科：通过适配器接入 HIS/EMR/LIS/SSO，不把医院差异扩散到业务核心。
- 医院管理者：获得可审计、可解释、可控风险边界的院内部署系统，而不是不可控医疗 Agent。

## 3. 商业千万级项目对标维度

| 维度 | 商业项目标准 | 当前差距 | 补齐方向 |
|---|---|---|---|
| 真实数据链路 | HIS/EMR/LIS/药品目录/SSO 适配器可替换，内部模型稳定 | 当前只有演示数据和 H2 profile | 建立真实连接器接口、映射版本、同步任务和提交前复核 |
| 医疗安全 | 硬规则、规则版本、病例测试、阻断不可绕过 | 已有最小规则雏形 | 扩展规则管理、审核发布、剂量计算、交互冲突与边界病例 |
| 证据治理 | 原始文件、解析块、片段、审核、发布、撤回全链路 | 当前为确定性演示证据 | 建立 EvidenceDocument/DocumentBlock/EvidenceChunk 审核流程 |
| 推荐闭环 | 候选、排除、医生修改、药师复核、草稿回写、最终状态回调 | 已有医生审核和模拟草稿 | 增加正式状态同步、过期推荐、复核任务、幂等回写 |
| 权限审计 | OIDC/SSO、角色科室权限、审计不可删、调试权限隔离 | 当前仅开发放行 | 实现 RBAC/ABAC、上下文票据、审计链和超级管理员约束 |
| 数据资产 | 患者药学档案、长期用药事件链、科研数据集冻结 | 数据对象尚未完整实现 | 实现事件链、反馈、队列、变量字典、数据质量和冻结版本 |
| 运维交付 | 容器、备份恢复、监控、压测、安全扫描、升级回滚 | Compose 基线初步 | 补 OpenTelemetry、备份脚本、恢复演练、CI/CD 和发布包 |

## 4. 新旧口径冲突处理

旧 MVP 口径：第一开发阶段不连接真实 HIS，使用模拟数据和 HIS 模拟器。

新商业交付口径：开发实现必须以真实数据链路为目标，不使用 Mock 或硬编码数据作为功能实现基础；模拟数据只作为导入验证、自动化测试和演示种子。

执行规则：

1. 业务核心代码不得依赖 `fixtures/his` 作为运行事实来源。
2. `fixtures/his` 只能通过导入器写入正式数据表，再由同一套 API 读取。
3. HIS 模拟器保留为“适配器测试替身”，不能绕过真实适配器接口和统一模型。
4. 所有推荐、审核、审计、草稿回写和反馈都必须走 Core API、数据库和任务表。
5. 没有医院真实接口时，先实现连接器契约、映射版本和导入链路，使用模拟导入验证，不把 UI 写成静态样例。
